# 문서 종류별 적용

**`--profile` 은 2층 검사기 `scripts/check.py` 의 플래그** — 1층 `doc-style-check.py` 에 주면 모르는 플래그로 rc 1 이 된다.

| 값 | 대상 | 형식 | 추가 원칙 |
|---|---|---|---|
| `general` | 일반 업무 문서 | 구조형 | 정확하고 평이한 표현 우선 |
| `technical-report` | 기술 검토·설계·시험 보고 | 구조형 | 식별자 보존 · 원인과 결과 구분 · 기술용어 임의 번역 금지 |
| `executive-report` | 임원·의사결정 보고 | 구조형 | 결론·기한·상태 우선 · 내부 코드명만 단독 사용 금지 |
| `presentation` | 슬라이드 본문 | 구조형 | 한 화면의 정보량과 강조 제한 · 짧아도 조사에서 끊지 않음 |
| `presenter-notes` | 발표 대본·발표자 노트 | **산문형** | 압축 명사구를 풀고 말로 설명되는 문장 사용 · 계획과 진행 상태 구분 |
| `short-message` | 제품 안내·업무 메시지·안내 메일 | **산문형** | 인사말·접속사·완곡 표현을 늘리지 않고 필요한 행동 명시 |
| `ct-project` | CT 프로젝트 문서 | 구조형 | CT 관련 사용자 확정 표현 적용 |

### 표에 없는 종류를 만났을 때

**백서·설명문·블로그 글처럼 줄글로 읽히는 문서에는 전용 값이 없다.** 가까운 종류를 고르고 형식만 산문형으로 바꾼다.

| 문서 | 고를 값 | 형식 |
|---|---|---|
| 기술 백서 · 기술 설명문 | `technical-report` | 머리말에 `form: prose` |
| 일반 설명문 · 소개 글 | `general` | 머리말에 `form: prose` |

**전용 값을 안 만든 이유** — 새 값을 만들어도 규칙 묶음은 `general_it_business` 그대로라 검사 결과가 달라지지 않는다. 백서에서만 걸리는 규칙이 실제로 확정되면 그때 만든다.

## 구조 규칙의 적용 범위

- 라벨:값과 개조식 종결은 보고서·슬라이드처럼 찾아보는 문서에 적용한다.
- 설명문·발표자 노트·서술형 보고서에 개조식 규칙을 일괄 적용하지 않는다.
- 문서 종류가 섞이면 섹션별로 판단한다. 예를 들어 슬라이드 본문과 발표자 노트는 별도로 검사한다.

### 형식을 전역 문서 검사기에 넘기는 법

위 표의 형식이 **산문형**이면 전역 문서 검사기에 `--form prose`를 붙인다. 안 붙이면 개조식을 전제한 검사가 정상 문장을 지적한다 — 안내 메일 실측에서 「안녕하세요 …입니다.」와 「감사합니다.」까지 오류로 잡혀 아홉 건 전부 오탐이었다.

```powershell
python "$HOME/.claude/assets/doc-style-check.py" <문서> --form prose
```

- **문서 자신이 형식을 들고 다니게 하려면** 머리말에 `form: prose`를 적는다. 훅이 자동으로 검사할 때도 적용된다.
- **끄는 것**: 서술형 종결 · 제목 서술형 · 제목 명사형 위반 · 진입점 서술형·없음
- **그대로 도는 것**: 절단형 종결 · 모호한 지칭 · 스캔 가치 없는 라벨 · 평가 수식어 — 산문에서도 잘못이다
- **형식을 안 적었는데 산문으로 보이면** 검사기가 「형식 미표기」 주의 한 줄로 물어본다. 짐작해서 끄지 않는다 — 표와 라벨이 뼈대인 문서에 근거 문단이 이어지는 형태를 산문으로 넘기면 정당한 지적이 조용히 사라진다.

## 조사 보고서 — 사용자가 정한 원칙

**조사·동향 보고서를 `technical-report` 로 검사할 때 9단계에서 함께 본다** — 사용자가 기술 조사 보고서를 두고 정한 것이다(2026-09-23~28). 검사기에는 없다 — 조사 보고서인지는 문서 전체를 봐야 갈리고, 같은 표현이 작업 기록에서는 정당하다.

| 원칙 | 내용 |
|---|---|
| **조사 과정 표시 금지** | 「2차」·「미확인」·「대조」·「(진위 미확인)」·「외부 모델이 반박함」·노트 번호를 공유 자료에 적지 않음 · 조사는 조사에서 끝냄 |
| **「찾지 못함」 대신 현황** | 「산업 실증을 찾지 못했다」(조사 행위) → 「연구 단계 — 가장 앞선 공개 결과는 ○○」 · 「공개 자료 기준」은 조사 범위 절에 한 번 |
| **권고·주장을 세우지 않음** | 「~해야 함」·「설계가 필요」 같은 당위 문장 삭제 · 카드 「주장」→「요지」 |
| **검증 기법 음차 금지** | 솔버·뮤턴트·퍼징 → SMT solver · mutant · fuzzing · 굳은 말(커버리지·벤치마크·프롬프트)은 그대로 |
| **참조는 링크** | 「아래 「○○」에 정리」처럼 제목만 적지 않음 |
| **긴 문장의 하위 불릿** | 원문을 해치지 않으면서 읽기에 유리할 때만 · 인과로 이어진 문장은 쪼개지 않음 · 한 출처의 인용은 한 불릿 |
| **수치 표보다 문장 요약이 먼저** | 사용자 말로 「표에 적힌 수치도 사실 전혀 읽을 수 없다. 문장으로 요약하는 것이 훨씬 낫다」 |
| **근거보다 결론을 먼저 던지지 않음** | 결론 줄 앞에 그 결론이 나온 근거가 보여야 함 — 첫머리의 결론이 「뜬금없이」 읽힘 |
| **첫 페이지만 읽어도 되는 구성** | 인사이트 제목 목록과 영역별 현재 수준 표를 요약 첫 페이지에 둠 |

**언어 규칙 밖 — 원문 대조로 본다** — 최종 검토에서 발행을 막은 것은 대부분 문체가 아니라 원문과의 사실 어긋남이었다. 요약에서 빠진 수치 조건 · 문자열은 맞는데 의도가 다른 인용 · 대상마다 근거가 다른데 한 문장으로 묶은 부정 · 모회사 이름으로 난 발표를 「없음」으로 적은 것 · 떨어진 두 조각을 이어 만든 인용. 이 검사기의 범위가 아니다 — 확인할 문장에서 원문 인용을 뽑아 본문과 문자열로 대조한다(전역 규칙 「웹·문서 확인」).
