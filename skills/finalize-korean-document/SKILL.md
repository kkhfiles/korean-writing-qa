# 한글 문서 최종화

문서의 사실과 의도를 보존하면서 AI 특유의 압축 표현·막연한 비유·번역투를 줄인다. 확정 규칙은 검사기로 찾고, 문맥이 필요한 표현은 직접 판단해 최소한으로 고친다.

## 실행 기준

- `scripts/...`로 시작하는 명령은 이 `SKILL.md`가 있는 디렉터리에서 실행한다. 다른 디렉터리에서는 스킬의 절대 디렉터리를 앞에 붙인다.
- 피드백 후보와 QA 사본의 기본 디렉터리는 `P:/github/korean-writing-qa`다. 다른 복사본을 쓸 때만 `KOREAN_WRITING_QA_HOME`을 해당 디렉터리로 지정한다.
- 자연스러움 기준문에는 판단에 쓴 원본 한 줄과 해시가 들어 있어 자체 시험만 실행할 때 원본 문서 사본이 없어도 된다.

## 작업 순서

1. 문서 종류와 독자를 정한다. `references/document-types.md`에서 가장 가까운 종류를 하나 고른다.
2. 검사할 편집 원본을 정한다.
   - Markdown·HTML·텍스트에서 다른 형식으로 변환했다면 편집 원본만 검사한다.
   - Word·PowerPoint를 직접 만들거나 고쳤다면 해당 형식 스킬로 표시 문구를 추출해 임시 UTF-8 텍스트로 검사한다.
   - PDF만 있고 편집 원본이 없다면 PDF 스킬로 텍스트를 추출하되, 추출 오류 가능성을 결과에 밝힌다.
3. `references/core-rules.md`와 선택한 문서 종류 규칙을 읽는다. 표에서 끝 칸에 `<!-- 개인 -->` 이 붙은 행은 개인 항목이다 — 개인 설정 파일(`local-personal-rules.txt`, 찾는 곳은 `data/catalog/local-personal-rules.example.txt`)이 있을 때만 적용하고 없으면 그 행을 건너뛴다. 판정 스크립트는 이것을 스스로 가른다.
4. `python scripts/check.py <대상> --profile <문서-종류>`로 확정 표현과 비유 후보를 검사한다.
5. **단어 점검을 돌린다** — 업무 글에서 드물게 쓰는 낱말을 목록으로 받는다.

```powershell
python -X utf8 P:/github/korean-writing-qa/scripts/rare_words.py <대상>
```

   - **이 단계에 둔 이유** — 검사기 규칙은 **이미 짚힌 짝만 안다**(고정 목록). 새 낱말은 원리적으로 못 잡는다. 사용자가 여섯 차례 짚어 준 것이 전부 그 갈래였고, 빈도로 보는 이 도구가 새 낱말을 잡는 **유일한 기계**다(2026-09-16 확인).
   - **⚠️ 판정하지 않는다 — 목록만 낸다.** 드문 것이 곧 틀린 것은 아니다(제품 이름·전문 용어·숫자 단위가 드문 것은 정상이다). 짝으로 가른다 — 「돈을 걷다」는 있고 「커밋을 걷다」는 없다.
   - **정상이라 판정하면 목록에 넣어 다음부터 접는다.** 낱말만 열지 말고 **어디서 정상인지**를 함께 적는다 — 「명사」는 이 저장소 글에서는 정상이지만 업무 보고서에서는 걸려야 한다.

```powershell
python -X utf8 P:/github/korean-writing-qa/scripts/rare_words.py --accept <낱말/품사> --context <정상인 문맥> --scope <경로 무늬> --why <근거 한 줄>
```

   - **이 저장소 밖 경로로 범위를 좁히면 `--local` 을 붙인다** — 저장소 밖 목록(`data/catalog/local-known-words.jsonl` · 공개 안 됨)에 들어간다. 안 붙이면 거절한다 — 공개 목록에 남의 프로젝트 경로가 나가기 때문이다.
   - **⛔ 목록은 면죄부가 아니다** — 다른 말로 바꿔야 하는 낱말은 넣지 않는다.
   - **끝냈으면 판정과 함께 적는다** — 남길 낱말을 다 가렸으면 `pass`, 고칠 것이 남았으면 `fail`. 중간에 멈췄으면 적지 않는다.

```powershell
python -X utf8 ~/.claude/assets/check_record.py record <대상> --stage words --verdict <pass|fail>
```

   - **발행 게이트는 이 기록을 요구하지 않는다** — 2층 판정기(`judge_layer2.py`)가 같은 목록을 판단 후보로 함께 받는다(2026-10-23 사용자 결정 · 대장의 단어 점검 몫 33건 중 32건을 짚음). 판정기를 못 부르는 PC 에서는 이 단계가 새 낱말을 잡는 유일한 기계라 그대로 한다.

6. 결과를 구분해 처리한다.
   - `suggest_exact`: 문맥과 의미가 같으면 제안문으로 고친다.
   - `review_context`: 앞뒤 문장과 실제 상태를 확인한 뒤 다시 쓴다. 제안문을 그대로 복사하지 않는다.
   - `abstract_candidate`: `경로`가 파일 위치나 실제 이동 흐름이 아니라 단계·방법·절차를 뜻하는지 확인한다.
7. 원문과 수정문을 비교한다. 제품명·조직명·사람 이름처럼 자동 추출이 어려운 고유명사는 `--protect`로 함께 넘긴다.

```powershell
python scripts/check_meaning.py <원문> <수정문> --protect <보존할-표현> --strict
```

   결과 상태에 따라 다르게 처리한다.

   - `preserved`: 다음 단계로 간다.
   - `meaning_marker_drops`: 상태와 무관하게 함께 나온다. 낱말은 다 남았는데 **뜻을 지탱하는 표지가 줄어든 곳**을 가리킨다 — 인과·조건, 계획과 완료, 부정과 범위, 추정과 단정, 행위 주체. 막지는 않으므로 그 자리를 직접 읽고 원문이 말하던 것이 남았는지 확인한다. 좋은 수정에서도 열에 하나쯤 걸리므로 지적으로 읽지 않는다.
   - `meaning_marker_sentences`: 위 개수가 어느 문장 짝에서 났는지 원문과 수정문을 나란히 보여 준다. 추정·유보는 **늘어난 것도** 낸다 — 일어난 일을 「~했을 수 있습니다」로 흐린 수정이 여기서 보인다. 그 짝만 읽고 원문이 말하던 확실성 정도가 남았는지 본다.
   - `change_rate_level`: 원문 대비 변경률이 `warn`(30% 이상)이나 `high`(50% 이상)이면 원문과 나란히 놓고 주체, 평가 대상, 주장 범위가 그대로인지 다시 읽는다. 남이 쓴 초안을 고치면 정당하게 많이 바뀌기도 하므로 막지 않는다.
   - `removed_content`: 보호 표현이 사라지기만 했다. `protected_removed`의 표현을 **하나씩** 확인해, 일부러 지운 것이면 `--expect-removed <표현>`을 붙여 다시 실행하고, 실수로 빠진 것이면 수정문에 되살린다. 무엇을 왜 지웠는지 사용자에게 함께 보고한다.
   - `changed_protected_content`: 값이 바뀌었거나 없던 표현이 생겼다. 수정문을 고친다. `--expect-removed`로 넘기지 않는다.

   중복 제거·군더더기 삭제·영어 낱말을 한국어로 바꾸기는 `removed_content`로 나온다. 이 규칙들이 권장 수정이므로 상태 자체는 문제가 아니고, **지운 것을 말하지 않고 넘기는 것**이 문제다.

8. 확정 표현 검사를 다시 실행한다. Markdown·HTML이면 기존 문서 구조 검사도 실행한다.

```powershell
python scripts/check.py <수정문> --profile <문서-종류> --strict
python "$HOME/.claude/assets/doc-style-check.py" <수정문>
```

   `references/document-types.md`에서 그 종류의 형식이 **산문형**이면 뒤 명령에 `--form prose`를 붙인다. 안 붙이면 개조식을 전제한 검사가 정상 문장을 지적한다. 형식이 구조형이면 그대로 둔다 — 짐작해서 끄면 정당한 지적이 조용히 사라진다.

   **형식은 파일이 들고 있게 한다.** Markdown은 머리말 `form: prose`, HTML은 `<meta name="form" content="prose">` 한 줄이다. 플래그로만 두면 검사할 때마다 사람이 기억해야 하고, 기억해야 하는 구조는 실패한다. 둘 다 있으면 플래그가 이긴다.

   **모르는 플래그는 rc로 멈춘다** — 예전에는 조용히 무시했다. `--relaxd`처럼 한 글자 틀리면 끄려던 검사가 안 꺼진 채 통과로 읽혔다. 검사기 자체 시험은 `python "$HOME/.claude/assets/doc-style-check-test.py"`다.

   **이어서 2층 판정 스크립트를 실행한다** — 스크립트가 문서와 판단 규칙 전문(`core-rules.md` + 9단계)을 모델에 전달해 지적 목록을 받는다. 지시 파일(CLAUDE.md와 AGENTS.md)은 전달하지 않는다. 점검표(2026-09-29)에서 이 판정문으로 고칠 어절 47/48을 잡았다. 2층 탐침과 같은 프롬프트를 쓴다.

   **「별도 호출」은 현재 대화와 분리된 검사 요청을 뜻한다** — 같은 AI 서비스에서 검사할 수 있으며, 다른 서비스나 다른 모델을 사용해야 한다는 뜻이 아니다. **⛔ 세션이 다른 AI 서비스나 모델을 찾아 따로 호출하지 않는다.** 지정된 판정 스크립트를 사용한다.

   **검사 백엔드를 지정하지 않았다면 현재 세션과 같은 서비스를 명시한다** — Codex 세션은 `--backend codex`, Claude Code 세션은 `--backend claude`를 사용한다. `auto`는 현재 세션을 식별하지 않고 설치된 Claude를 먼저 선택하므로, 같은 서비스를 유지하려는 호출에서는 생략하지 않는다. 사용자가 검사 백엔드를 지정했다면 그 지정을 따른다. 호출할 수 없으면 다른 서비스로 임의 전환하지 않고 아래 「종료 코드」 항목대로 직접 판정한다.

   **Codex 세션은 판정 명령만 샌드박스 밖 실행으로 승인을 요청한다** `[2026-10-20 사용자 결정]` — Codex 샌드박스(`network_access: false`)는 판정기의 모델 호출을 막는다. 10-14~10-20 Codex 세션의 판정이 매번 「모든 모델 시도 실패」로 끝났고, 같은 세션의 다른 HTTP 요청도 연결 거부였다. 네트워크를 전역으로 열지 않고, 판정 명령을 부를 때마다 샌드박스 밖 실행을 요청한다. 실패 글에 「네트워크 오류(Codex 샌드박스 안이면 밖에서 실행)」가 보이면 이 경우다.

```powershell
# Codex
python -X utf8 P:/github/korean-writing-qa/scripts/judge_layer2.py <수정문> --backend codex
# Claude Code
python -X utf8 P:/github/korean-writing-qa/scripts/judge_layer2.py <수정문> --backend claude
```

   - **git 저장소의 가지에서 고친 문서는 `--since origin/main`** — 그 가지와 갈라진 뒤 새로 생겼고 판정기가 아직 안 본 줄만 판정하고, 그 줄에 달린 지적만 보여 준다. 지적 목록을 **한 묶음으로 처리(고침 · 사유 · 사람 확인)한 뒤 같은 명령을 한 번 더** 부르면 고친 줄만 다시 판정한다. **지적 하나 고칠 때마다 부르지 않는다** — 호출마다 문서 문맥을 다시 실어 토큰이 들고, 같은 줄의 판정 횟수가 빨리 쌓여 재판정 상한(사람 확인)에 먼저 닿는다(2026-10-13 한 문서에서 판정 58회 중 29회가 대상 3줄 이하였다). 고치는 방향이 맞는지 먼저 봐야 하는 대표 수정은 한두 건 고쳐 중간에 판정해도 된다 — 사실 주장을 좁히거나 지운 줄도 확인할 사실이 바뀌므로 「확인함」을 적기 전에 다시 판정해도 된다. 고친 말이 새 문제를 들여오는지 보는 것이 이 재판정의 몫이다(실문서에서 수정안 40건 중 8건이 되돌아옴). 「판정할 새 줄 없음」이 나오면 끝이다.
     - **고친 줄은 기준 판과 함께 간다** (2026-10-12) — 갈라진 지점의 원래 줄과 근처에서 지운 줄을 판정기가 함께 받아, 숫자 · 주체 · 부정 · 조건 · 범위 · 확실성이 달라졌거나 필요한 정보가 빠졌으면 「고치다 뜻이 바뀐 곳」으로 짚는다.
     - **같은 줄은 세 번까지 다시 판정한다** — 넘으면 그 줄의 지적은 사람 확인으로 바뀌고, 그 줄 자체도 기준 판과 함께 사람 확인에 오른다(「재판정 상한」). 상한에 닿았다고 통과시키지 않는다 — README 고리 시험에서 5회차에야 원문의 실제 결함을 짚었다. 한 줄을 나눠도 판정 횟수는 이어진다.
   - **push 직전 게이트** — 뿌리의 `korean-qa.toml` 에 `[publish]` 를 둔 저장소(lab-docs)는 push 직전에 **커밋된 내용**으로 두 가지를 본다. 새 줄을 판정기가 다 봤는가(판정기를 부를 수 있는 PC 에서만) · 12단계의 판단 기록이 있는가. 그래서 판정과 기록을 마치고 **커밋한 뒤** push 한다.
   - **판정 뒤 고친 줄도 판정해야 발행된다** (2026-10-13) — 판정 기록이 있는 문서(또는 `[publish]` 대상)는 발행 직전 검사가 판정기가 아직 안 본 한글 줄을 막는다. 마지막 묶음을 고친 뒤 `--since` 를 한 번 더 부르고 발행한다. 판정기를 부를 수 없는 PC 에서는 규칙을 직접 읽고 지금 내용에 판단 기록(`judgment`)을 남긴다.
   - **목록을 그대로 반영하지 않는다** — 지적마다 맞는지 판단한다. 헛짚음이 섞인다(점검표 「그대로」 줄 2/9).
   - **고칠 지적도 처리해야 발행된다** (2026-10-12) — 고칠 지적은 판정 기록에 남고, 짚은 표현이 그 줄에 남아 있는 동안 발행 직전 · push 직전 · 배포 직전 검사가 막는다. 지적마다 셋 중 하나로 처리한다.
     - **고친다** — 고친 줄은 묶음을 다 처리한 뒤 `--since` 로 한 번에 다시 판정한다. 고칠 때 숫자 · 주체 · 부정 · 조건 · 범위 · 확실성이 원문과 같은지 본다 — 수정안이 경위 문장을 다른 주장으로 바꾼 사례가 있다(2026-10-12 고리 시험).
     - **받지 않는다** — `--dismiss <행> --reason <사유> --note "근거"`. 사유는 대상아님 · 오독 · 충족(근거에 「N행」) · 규칙충돌 · 확인함(근거에 자료 경로 · 명령) · 지시반영 가운데 하나다. 번거로움 · 상한에 닿음 · 예전에도 허용 · 아마 맞음은 사유가 아니다. 기록은 그 지적 하나에만 듣고, 그 줄이 바뀌면 다시 열린다.
     - **「지시반영」은 일부러 바꾼 뜻에만** (2026-10-13) — 「고치다 뜻이 바뀐 곳」 지적을 사용자 · 검토자 지시대로 바꾼 것이면 이 사유로 닫고, 근거에 지시 원문을 「」로 옮겨 적는다(누가 · 언제와 함께). 지시는 편집 의도의 근거이지 사실의 근거가 아니다 — 사실 확인 지적은 「확인함」이나 사람 확인으로 닫는다.
     - **지시로 바꾼 줄은 다시 판정하기 전에 지시를 적는다** (2026-10-16) — `--instructed <행> --note "사용자 지시 「…」(누가 · 언제)"`. 재판정이 지시 안의 뜻 변경은 짚지 않고, 지시 밖의 변경 · 확인이 필요한 새 주장 · 다른 규칙 위반만 짚는다. 짚인 뒤 하나씩 「지시반영」으로 닫는 수고가 준다(사내 문서 1건에서 그런 닫기가 46건 중 40건). 지시 원문은 사용자가 한 말을 옮긴다 — 세션이 지어내지 않는다.
     - **근거는 기계가 대조한다** — 확장자가 붙은 경로는 실제 파일이어야 하고, 경로 바로 뒤의 「인용」은 그 파일에 글자 그대로 있어야 하며, 「N행」은 그 파일(경로 뒤)이나 문서 범위 안이어야 한다. 절 제목 · 원문을 바꿔 적으면 거절된다.
     - **세션이 정할 수 없으면 사람 확인으로 올린다** — `--escalate <행> --note "무엇을 누가 확인해야 하는지"`.
     - **「[사실 확인]」 지적은 받지 않음으로 닫지 못한다** — 근거에 「확인 필요」가 걸린 지적이다. 저장소 · 원자료로 확인할 수 있으면 확인해 고치거나 「확인함」으로 닫고, 담당자 · 비공개 측정처럼 세션이 볼 수 없는 자료면 사람 확인으로 올린다. 확인 못 한 사실을 짐작으로 고치지 않는다.
   - **「사람 확인」 지적은 세션이 정하지 않는다** — 판정기가 고칠지 정하지 못해 넘긴 것이다(2026-10-06 사용자 「규칙으로 잡고 llm 판단으로 잡고, 그래도 애매하면 사람한테 애스컬레이션」). 답을 못 받은 지적이 남은 문서는 발행 직전 검사와 push 직전 게이트가 막는다.
   - **묻는 형식은 판정기가 만든다 — 10건 이하는 대화, 넘으면 md 표** (2026-10-07 사용자 「최소한 md 파일에 표 형태로 정리라도 해줘야 사람이 하나씩 본 뒤에 판단할 것 아닌가」 · 2026-10-13 사용자 「10개 이하일 경우에는 그냥 화면에서 보여줘도 될 듯」) — 건수와 상관없이 `--sheet` 로 표를 만든다. 표에는 묻는 순간의 줄 해시가 들어 있어, 그 뒤 바뀐 줄의 답을 거른다. 지적이 10건 이하면 `--sheet` 가 같은 번호(Q1 …)의 목록을 화면에 내니 그 목록을 대화로 그대로 보이고 묻는다. 넘으면 표 경로를 사용자에게 준다 — 61건을 대화로 넘겼다가 사람이 하나씩 볼 수 없었다. 목록이나 확인 페이지를 손으로 만들지 않는다. 표는 한 줄이 한 행이고, 문장(짚은 표현 굵게) · 갈래 · 판정기 제안 · 넘긴 까닭 · 빈 「답」 칸을 갖는다. **표 안에 문서 글이 들어가므로 저장소 밖에 둔다.**
   - **대화로 받은 답은 `--answers-from <표> --reply "Q1 그대로"` 로 읽는다** — 사용자가 한 말을 번호별로 원문 그대로 옮긴다. 답하지 않은 번호는 적지 않는다. 표 답 칸과 같은 검사(줄 해시 대조 · 답 기록 · 고칠 목록)를 거친다.
   - **사용자가 「답」 칸을 채우면 `--answers-from` 으로 읽는다** — `그대로` 만 답 기록에 남고, `고침` · `직접: …` 은 고칠 목록으로 나온다. **답대로 고친 줄은 사람이 판정한 줄로 확정해 다시 판정하지 않는다** (2026-10-14) — `고침` 은 판정기 제안을 글자 그대로 넣으면 저절로 확정된다(다르게 고치면 다시 판정한다). `직접: …` 은 사용자 답대로 고친 뒤 `--answer <행> --note "<사용자 원문>"` 으로 확정한다. 확정하지 않고 `--since` 를 부르면 그 줄은 다시 판정되고, 재판정 상한을 넘은 줄이면 판정기가 판정마다 새로 짚은 표현이 다시 사람 확인으로 간다(lab-docs 출처 소개 한 줄에서 네 번 물음). 나머지 고친 줄은 `--since` 로 다시 판정한다. `보류` · 빈칸은 열린 채 남는다. 넷 가운데 하나로 시작하지 않는 글(「이건 그냥 놔두자」 · 「빼는게 낫겠다」)은 「글로 적은 답」으로 따로 나온다 — 원문을 읽고 고칠 뜻이면 고치고, 유지하는 뜻이 분명하면 `--answer <행> --note "<사용자 원문>"` 으로 남긴다. 뜻이 갈리면 다시 묻는다. 표를 만든 뒤 바뀐 줄의 답은 받지 않으니, 문서를 고쳤으면 표를 다시 만든다.
   - **읽은 답은 다음 판정이 따른다** (2026-10-07 사용자 「내 기본 답변을 기반으로 판단했으면 좋겠는데, 현재 AI가 애스컬레이션한 항목이 너무 많다」) — `--answers-from` 이 답을 모두 답 기록(`korean-layer2-decisions.jsonl`)에 남기고, 판정기는 그 기록을 프롬프트로 읽는다. ⛔ 갈래별 고침 횟수로 사람 확인을 고칠 지적으로 바꾸던 장치는 뺐다(2026-10-12) — 바뀐 5건이 모두 문서만으로 못 가르는 사실이었고, 고침 답은 낱말을 고친 것이라 그 근거가 못 된다.

9. 검사기가 못 잡는 것을 직접 찾는다. 검사기는 확정 표현과 `경로` 비유만 본다. `references/core-rules.md`의 나머지 원칙은 사람이 판단해야 하므로, 검사 결과가 비어 있어도 문서를 읽고 확인한다. **검사기가 조용한 것은 깨끗하다는 뜻이 아니라 그 규칙을 안 봤다는 뜻이다.**

   특히 아래 갈래는 **줄 하나만 봐서는 못 가른다.** 문장은 멀쩡하고 문서 전체의 의도와 대조해야 드러나므로 검사기에 넣지 않고 이 층이 본다(사용자가 짚어 준 것에서 왔고, 항목마다 날짜를 적었다).

   - **당연한 말** — 읽는 사람이 이미 아는 것을 굳이 적어, 없는 제약이 있는 것처럼 읽히게 한다. 「원래 못 보던 자료가 검색으로 보이지 않음」(권한 체계가 있으면 당연) · 「넷 가운데 골라 씁니다. 넷을 매번 다 쓰지는 않습니다」(앞 문장이 이미 말했다). **판정 — 지우고 읽어서 잃는 것이 없으면 군더더기다.**
   - **가치를 못 살린 제약** — 설계 결정을 「안 하는 것」으로만 적어 약점처럼 보이게 한다. 「개인 메일·소스코드 본문은 안 담음」은 사실이지만, 실제 설계는 개인 자료를 본인 색인에만 두고 본인이 검색할 때만 잇는 것이다. **판정 — 그 항목이 왜 그렇게 설계됐는지 물어 보고, 답이 이점이면 이점으로 적는다.** 제품 매뉴얼의 제한 항목을 「이 도구는 ~를 확인하지 않으므로」처럼 도구 주어 부정문으로 옮기면 도구가 실제로 지원하는 기능까지 없는 것처럼 읽힌다(2026-10-22 대외 기술 백서 인계 · 사용자가 도구 주어가 어색하고 그 도구는 해당 시험도 지원한다고 짚음). 제한의 범위를 원문과 대조해 확인한다.
   - **예시를 대표값으로 올림** — 지금 이어 붙인 대상 수를 대표값으로 쓰면 더 늘릴 수 있다는 사실이 사라진다. **판정 — 그 숫자가 제품의 한계인지 오늘의 현황인지 확인한다.**
   - **고치다 논리를 깬 곳** — 말투를 다듬는 과정에서 문장이 말이 안 되게 바뀐 곳이다. 뜻이 바뀐 것과 다르다. 「따로 기록하지 않는 업무 비서」(기록은 남는다 · 사람이 안 적을 뿐이다) · 「물으면 아무도 기록하지 않습니다」(조건과 결과가 안 맞는다). **판정 — 고친 문장만 따로 소리 내어 읽고, 주어가 그 서술을 할 수 있는지와 조건이 그 결과로 이어지는지를 본다.** 둘 다 2026-09-14 에 사용자가 짚었고, 둘 다 **바로 앞 회차에서 내가 고치며 만든 것**이다.
     - **고치면서 원문에 없던 대구나 결산 꼴을 새로 넣음** (2026-10-23) — 다듬은 문장에 원문에 없던 「A가 아니라 B」, 문단 끝 「결국 ~로 이어집니다」, 「~하는 이유입니다」가 새로 생긴 경우다. AI 글 윤문 도구 im-not-ai 가 자기 윤문 결과에서 실측한 역주입이고, 업무 문서에서도 「A가 아니라 B」는 AI 글이 사람 글보다 열 배 많이 쓴다. **판정 — 수정안을 내기 전에 원문 문장에 그 꼴이 있었는지 본다.** 없던 꼴이면 뒷말을 바로 단언한다(「품질 확보가 목적입니다」). 원문에 있던 꼴은 이 항목으로 고치지 않는다. 같은 갈래로 「첫째, 둘째, 셋째」 열거를 문장으로 풀면서 앞의 「세 가지가 있습니다」 예고만 남기면 수를 약속하고 항목 표지는 사라진다 — 열거를 풀었으면 예고도 함께 고친다(im-not-ai 후보 C-1-R).
   - **한 낱말로 있는 행위 명사를 동사구로 품** — 「구분」을 「갈라서 냄」으로, 「통합」을 「열어 합치기」로, 「검토」를 「다 보는 데」로, 「제시」를 「후보만 내고」로, 「입력」을 「공수 넣기」로 푼 것이다. **빈도로는 못 가른다** — 쓴 동사가 흔하기 때문이다(열 1,786 · 보 6,047 · 넣 2,695). **판정 — 그 구를 한 낱말로 바꿔 보고, 바뀐 쪽이 업무 문서에서 더 자주 보이면 바꾼 쪽이 맞다.** 2026-09-15 에 다섯 건을 확인했고, 원인은 전역 규칙의 「어려운 말로 쓰지 않음」이었다(그날 지웠다).
   - **관형형 + 흔한 명사로 만든 구** — 「같이 나온 **것**」·「담기는 **단계**」처럼 앞말이 뜻을 다 지고 뒤 명사는 붙어만 있는 꼴이다. **기계로 못 옮긴다** — 실문서 644개에서 「관형형 + 것」이 1,235건, 「관형형 + 단계」가 18건인데 「사람이 한 번 읽는 단계」·「채워 넣는 단계」처럼 정당한 것이 사실상 전부다(2026-09-16 실측). 검사기의 「지어낸 명사구」가 쓰는 판정(그 명사가 혼자 서나)으로도 안 갈린다 — 「것」도 「단계」도 혼자 선다. **판정 — 뒤 명사를 지우고 앞말만 남겨 읽어 본다. 뜻이 그대로면 군더더기다.**
   - **선행사 없는 「그 앞」·「그 뒤」** — 무엇의 앞뒤인지가 같은 줄에 없는 경우다. 실문서에서 8건인데 「그 뒤 2주 동안」·「그 뒤 어떻게 됐는지」처럼 앞 문장에 선행사가 있는 정당한 쓰임이 대부분이라 줄 단위 검사기가 못 가른다(전역 규칙이 「그 + 명사」를 사람에게 넘긴 것과 같은 판단). **판정 — 그 줄만 떼어 읽어 무엇의 앞뒤인지 말할 수 있는지 본다.** ⚠️ 「앞과 뒤」는 다르다 — 실측 0건이라 검사기가 오류로 잡는다.
   - **진행형으로 늘린 서술** — 「매일 **돌고 있는** 업무 비서」처럼 상태를 굳이 진행형으로 늘린 것이다. 실문서 46건이 **전부 정당**이라 규칙으로 못 만든다(2026-09-16). **판정 — 「도는」으로 바꿔 읽어 잃는 뜻이 있는지 본다. 없으면 늘린 것이다.**
   - **사물을 사람처럼 쓴 서술** — 「**아무도 안 기다림**」(배치 작업을 기다리는 사람이 없다는 뜻)·「표가 **스스로** 낡음」처럼 사물에 사람의 행위를 붙인 것이다. 「이 실험은 고침과 정상 중 하나를 **물었습니다**」·「규칙은 두 번째부터 **안 들으므로**」도 같은 갈래다(2026-09-29 점검표 · 사용자 「한국어에서 잘 사용하지 않는 주어」). 실문서에서 「아무도 안 ~」이 29건인데 「아무도 안 읽음」·「아무도 안 보고 있었다」처럼 사람이 주어인 정당한 쓰임이 대부분이다. **판정 — 주어가 사람인지 본다. 사물이면 그 사물이 실제로 하는 일로 바꾸거나, 「이 실험에서는 ~로 분류했습니다」처럼 사람이 한 일로 바꾼다.**
     - **표준, 조항, 문서, 「프로젝트」 같은 사물 이름을 주어로 씀** (2026-10-22 대외 기술 백서 인계) — 「이 표준은 두 용어를 구별합니다」·「제5절은 데이터 관리를 다룹니다」·「프로젝트는 도구 신뢰도를 확인합니다」. 사용자 말로 「표준이 주어로 쓰인 건 한글로 어색함」. 고칠 때는 「이 표준에서는 ~로 구별해 씁니다」·「제5절에서는 ~를 다룹니다」·「제5절에 따라 ~는 ~로 사용됩니다」처럼 범위나 근거를 나타내는 말로 바꾸거나, 행위를 하는 사람을 주어로 세운다. 회사나 기관이 발표하거나 밝히는 문장(「그 업체는 보고서에서 ~를 원인으로 밝혔습니다」)은 실제 조직의 행위라 정상이다. 한 곳이 짚히면 문서 전체에서 같은 꼴을 찾는다 — 그 문서는 21곳이었고 판정기는 세 번 판정하고도 한 곳도 짚지 않았다.
     - **정상 짝** — 「~은 ~를 다루는 표준입니다」 같은 지정문, 도구가 기능을 제공하는 문장(「이 도구는 시험 결과를 제공합니다」), 책임을 나누는 문장의 행위 주체(「승인은 개발 조직이 담당합니다」). 그 행위 주체도 문서 종류에 맞는 말로 고른다 — 백서에서 「프로젝트 팀」을 사용자가 다시 짚어 책임과 승인은 「개발 조직」(표준의 책임 주체 organization), 손으로 하는 작업은 「검증 담당자」로 바꿨다. 범위를 가리키는 「프로젝트의 요구사항」은 그대로 둔다. 표준 주어를 「~에서는」으로 바꾸면 「이 표준에서 ○○ 위험은 관련 조항을 확장해 다룹니다」처럼 목적어가 「은/는」으로 앞에 나오는데 정상 한국어다. 이것을 「위험을」로 고치면 같은 문장에 「을/를」이 둘 겹친다(2026-10-22 같은 문서의 AI 검토가 그렇게 고쳤다가 되돌림). 정규식 후보(「표준이나 조항 이름 + 은/는 … 다룹니다류」)는 그 문서 원본 21곳 중 5곳만 잡아 규칙으로 올리지 않았다 — 동사가 너무 다양하다.
   - **관형형 없이 홀로 선 은유 「자리」** — 검사기는 **관형형 + 자리**만 본다. 「그 자리가 틀리면」·「연동은 자리마다」처럼 앞에 관형형이 없으면 정규식에 안 걸려 발행본에 그대로 나갔다(2026-09-15 재검토). 선행사를 봐야 갈리므로 기계로 못 옮긴다 — 전역 규칙이 「그 + 명사」를 사람에게 넘긴 것과 같은 판단이다. **판정 — 「자리」를 지우고 그것이 가리키는 것(계산·대상·지점·단계)을 넣어 읽어 본다. 뜻이 또렷해지면 은유다.** 「그 자리에서 묻는다」(즉시)·「앞자리」·「한 자리에 모으다」는 굳은 쓰임이라 그대로 둔다.

   「판단어의 기준 누락」부터 「기호로 압축한 한 줄」까지는 기술 조사 보고서를 두고 사용자가 직접 짚은 것이다(2026-09-23~28, 다른 세션이 인계). 사용자는 「코멘트한 내용은 전체 자료 공통으로 살펴봐야 함」이라고 했다 — 짚은 한 곳은 문서 전체의 표본이라, 같은 갈래를 문서 전체에서 찾는다.

   - **판단어의 기준 누락** — 「맞는 코드」·「동작이 틀렸는데도」·「올바른 답」처럼 무엇에 비추어 맞고 틀린지가 없다. 같은 보고서 검토에서 41건이 나왔다. **판정 — 「무엇에 비추어?」를 묻고, 답(요구 충족·명세·의미상 오류)을 같은 문장에 넣는다.**
   - **원문 용어를 직역한 말** — 「약한 테스트」(weak tests)·「공허하지 않음」(non-vacuity)·「척추 문구」(spine). 단어 점검은 드문 낱말(공허·척추·체류)은 잡지만 흔한 낱말끼리의 직역(약한 테스트)은 못 잡는다. 명사 셋을 이은 표준 용어 직역(「안전 보증 논증」 ← assurance argument)도 낱말 하나하나는 흔해서 안 걸린다(2026-10-22 대외 기술 백서 인계 · 사용자 「한글로도 쓰는 말인지?」). 낱말 짝 빈도를 보는 점검은 아직 없다. 그 문서는 「안전 논증(assurance argument)」으로 바꿨다 — 낱말마다 옮긴 말이고 한국어 용례를 찾지 못했다. **판정 — 원문을 모르는 사람이 그 말만 보고 뜻을 말할 수 있는지 본다. 못 하면 뜻을 풀고 원문 표현을 괄호에 병기한다.**
     - **반대 방향 — 한국어 문장에 영문 용어만 남김** (2026-10-22) — 「이 활동을 AI model validation이라 하고」처럼 번역어 없이 원어만 둔 경우다. 사용자 말로 「그냥 영문만 썼는데 이상하지 않나?」. 「번역어가 현업에서 낯설다」는 근거 없는 사유로 영문만 남긴 것이었다. 한국어 용어 뒤에 원어를 괄호로 붙이고(「AI 모델 확인(AI model validation)」), 번역어는 같은 문서 안의 쓰임에 맞춘다.
     - **표준 절 제목을 옮긴 명사구를 목적어로 씀** (2026-10-22) — 「도구 사용에 대한 신뢰를 해당 절에 따라 확인합니다」처럼 절 제목을 그대로 옮겨 무엇을 하라는 것인지가 안 보인다. 사용자 말로 「좀 어색한데」. **판정 — 그 절에서 실제로 하는 일을 동사로 풀어 쓸 수 있는지 본다.** 풀 수 있으면 「도구 신뢰 수준을 정하고, 그 수준에 맞는 방법으로 도구의 적격성을 확인합니다」처럼 행위로 쓴다.
   - **요약하다 맥락이 빠진 명사구** — 「구문은 해결」(무엇을 잰 결과인지 없음)·「검증 모델이 실제 실행을 대표하는 범위」·「수용된 변경의 총비용」(정의 없는 지표 이름)·「재분석으로 검증」(무슨 분석인지 없음)·문서 첫머리의 명사구 나열. **판정 — 그 줄만 떼어 처음 보는 사람이 「무엇의 무엇을 어떻게」를 말할 수 있는지 본다.** 지표 이름은 첫 등장에 정의와 단위를 붙인다. 고친 말에는 「정의 필요」 같은 할 일 이름이 아니라 **고친 문장이나 넣을 정의**를 적는다 — 할 일 이름만 적은 수정안은 사용자가 「부연설명 필요」로 되돌렸다(2026-09-29). 원문에서 정의를 확인하지 못했으면 그 사실을 함께 적는다.
   - **공유 자료에 남은 작업 흔적** — 조사 과정(「외부 모델에 보내 반박을 받음」)·확인 상태 딱지(「(진위 미확인)」·「2차」·「미대조」)·내부 방침 번호·노트 번호. **판정 — 읽는 사람이 그 표시로 할 일이 있는지 본다. 없으면 지운다. 확인이 안 된 사실은 확인하거나 뺀다.** ⛔ 딱지를 다른 말로 바꿔 다는 것(「(진위 미확인)」→「(검증되지 않은 수치)」)은 고친 것이 아니다. 말을 다듬을 문제가 아니라 **확인 안 된 내용을 싣고 나가는 문제**라서, 발행 전에 확인하거나 지운다(2026-09-29 사용자 「불확실한 내용이 붙은 채로 배포하면 안됨」).
   - **읽는 사람에게 쓸모없는 문서 안내** — 「읽는 법」·「문서 구성」 같은 절과, 문서가 다룰 항목을 늘어놓기만 한 구성 설명. 사용자 말로 「쓸데없는 말이다. 읽기 쉽게 써주면 되는건데」. **판정 — 그 절을 지우고 읽어서 잃는 것이 없으면 지운다.** 기호 풀이처럼 꼭 필요한 내용이 들어 있으면 절을 지우지 말고 그 내용을 제목으로 삼는다(「읽는 법」→「표 기호의 뜻」). 진입점 한 줄(「문서 서술 규칙」의 「진입점」)은 이것과 다르다.
   - **기호로 압축한 한 줄** — 「MCP + 자동 수정 + 재분석 탑재 · 오탐 급증 → 확인 게이트」처럼 「+」·「→」와 가운뎃점으로 사실 여럿을 한 줄에 몰아넣었다. 전역 규칙이 값 칸의 「→」 하나는 권하므로 기호 자체는 결함이 아니다. **판정 — 기호를 말로 풀어 읽고, 사실이 셋 이상이면 하위 항목이나 문장으로 나눈다.**

   「접속어와 문장 관계의 어긋남」부터 「다듬다 원문의 논점을 바꿈」까지는 **문장 사이의 관계**다. 발표 원고를 고치며 찾은 사례에서 왔다(2026-10-20, 사례와 정상 짝은 `tests/fixtures/layer2-discourse/cases.jsonl`). 문장 하나는 멀쩡하고 앞뒤 문장이나 앞 절을 함께 읽어야 드러난다. **접속어, 지시어, 재귀 표현이 있다는 것만으로 짚지 않는다** — 같은 말을 쓴 정상 문장이 훨씬 많다. 짚을 때는 어긋남의 근거가 되는 앞뒤 문장을 근거에 함께 인용한다. 받은 글만으로 관계를 정할 수 없고 의도된 반전이나 발표 흐름처럼 글쓴이만 아는 것이 판정을 가르면 사람 확인으로 넘기고, 필요한 문맥을 근거에 적는다.

   - **접속어와 문장 관계의 어긋남** — 「그런데」 뒤가 앞 문장의 기대를 뒤집지 않고 다룰 주제를 고르기만 하거나, 「이런 변화 속에서」·「그 결과」 뒤의 주장이 앞 사례로 뒷받침되지 않아 주제 전환이 인과로 읽히는 경우다. **판정 — 접속어를 지우고 두 문장의 관계가 대조, 인과, 보충, 주제 전환, 범위 확대 중 무엇인지 먼저 정한 뒤 접속어와 대조한다.** 앞 계획이 실제로 뒤집히면 역접이 맞고, 앞 조치가 뒤 결과로 직접 이어지면 인과가 맞다.
   - **절 사이 연결의 어긋남** — 절을 잇는 문장이 앞 절에서 이미 한 관점 전환을 반전처럼 다시 시작하거나, 다음 사례로 넘어가는 까닭(앞 사례에서 이어지는 질문)을 빼고 소개만 하는 경우다. **판정 — 연결 문장이 앞 절을 정확히 정리하는지, 다음 절이 실제로 다루는 대상을 안내하는지 본다.** 문법 오류가 아니라 구성 문제라서, 고친 말은 앞뒤 절을 잇는 질문이나 범위로 쓴다.
   - **지시 대상이 흐린 지시어와 재귀 표현** — 「이 비교」·「이 차이」·「이런 변화」가 가리킬 후보가 앞에 둘 이상이거나, 주어가 바뀐 뒤 나온 「자신」이 의도와 다른 사람으로 읽히는 경우다. **판정 — 선행 대상을 원문에서 찾아 하나로 정해지는지 본다.** 후보가 하나뿐이거나 「자신」이 같은 문장 주어를 가리키면 정상이다. 여럿이면 대상이나 역할 이름으로 바꾼다.
   - **관찰 단위가 다른 자료를 한 기준으로 이음** — 개인 경험과 조직 지표처럼 대상 집단, 관찰 단위, 측정 항목이 다른 자료를 한쪽으로 다른 쪽을 반박하거나 뒷받침하듯 이은 경우다. **판정 — 두 자료의 대상과 단위와 측정 항목을 나란히 적어 보고, 다르면 무엇을 판단할 수 없는지 밝힌다.** 나란히 소개하고 대상이 다르다고 밝힌 글은 정상이다.
   - **감정 설명이 사람 평가로 읽힘** — 「담당자가 난처해 보였습니다」처럼 누군가 느낀 감정을 설명하려던 말이 그 사람에 대한 평가로 읽히는 경우다. **판정 — 감정의 당사자와 평가 대상을 갈라 본다.** 둘로 읽히면 누가 무엇 때문에 그 감정을 느꼈는지로 쓴다.
   - **한 서술어에 다른 행위를 몰아넣음** — 근거 설명과 의견 청취처럼 성격이 다른 행위를 「전달로 끝낸다」 같은 서술어 하나에 묶어, 무엇이 빠졌다는 뜻인지 흐려진 경우다. **판정 — 나열한 행위가 뒤 서술어와 각각 이어지는지 본다.** 이어지지 않으면 행위의 순서와 관계를 풀어 쓴다.
   - **권유를 가능 표현으로 돌려 말함** — 새로 가능해진 일이 없는데 청중에게 생각을 권하는 말을 「생각할 수 있게」·「느낄 수 있도록」처럼 기능을 주는 꼴로 쓴 경우다. **판정 — 그 문장 앞에 무엇을 실제로 가능하게 한 수단(화면, 도구, 자료)이 있는지 본다.** 있으면 정상이고, 없으면 「생각해 봅니다」처럼 직접 쓴다.
   - **다듬다 원문의 논점을 바꿈** — 인용이나 요약을 자연스럽게 고치면서 주체, 평가 대상, 주장 범위가 원문과 달라진 경우다. 「고치다 논리를 깬 곳」과 달리 문장은 말이 되고 원문과만 어긋난다. **판정 — 원문이 같은 문서에 있으면 요약과 원문의 주체, 평가 대상, 범위를 대조한다.** 원문이 문서에 없으면 뜻을 짐작해 메우지 않고 대조할 원문을 `check` 에 적는다.
     - **원문에 없는 기준을 들여와 설명을 덧붙임** (2026-10-22) — 표준이 세 용어의 뜻을 갈라 쓴다는 요점에 「영어로 모두 test가 들어가는 세 용어」처럼 원문의 논점이 아닌 기준을 덧붙인 경우다. 사용자 말로 「이게 중요한 건 아니잖니?」. 문장 하나는 멀쩡해서 기계로 못 가른다. **판정 — 덧붙인 수식을 지우고 원문의 요점이 그대로 남는지 본다. 남으면 지운다.**

   아래 항목은 AI 글 윤문 도구 im-not-ai 의 분류에서 왔다(2026-10-23). 업무 문서 표본에서는 거의 안 나왔지만 안 나온 것은 빼는 근거가 아니라서 넣었다. 줄만 보고 가를 수 있는 꼴은 검사기 「상투 문형」이 보고, 여기에는 문서 위치나 앞뒤 문장을 봐야 갈리는 것만 둔다.

   - **구체 경로 없는 결산과 결말 공식** — 문단 끝을 「결국 ~로 이어집니다」·「~에 직결됩니다」로 닫아 인과를 선언만 하거나, 글 끝부분 문장을 「향후」·「앞으로」·「중장기적으로」로 열어 시점과 조건 없이 전망을 붙이거나, 이전 상태를 앞에서 말하지 않고 「더 이상 ~이 아닙니다」로 재정의하거나, 「'규모의 경쟁'에서 '전략의 경쟁'으로」 같은 전환 슬로건을 거듭 쓰는 경우다. 같은 갈래로 「청구서가 날아온다」·「시장을 잠식한다」 같은 지어낸 은유를 한 문서에 여럿 겹친 것도 본다. **판정 — 그 문장을 지워도 앞 문장이 말한 것과 같은지 본다.** 같으면 지우고, 인과면 실제 경로(무엇이 줄고 무엇이 늘어나는지)를, 전망이면 원문에 있는 시점이나 조건을 쓴다. 원문에 없는 시점과 경로는 지어내지 않는다. 「다음 단계로 이어집니다」처럼 절차 순서를 말하는 것, 「결국 같은 문제가 났다」처럼 일어난 일의 결과를 말하는 것, 앞 문장에 이전 상태가 있는 「더 이상」은 정상이다.
   - **산문 문서에 얹은 개조식 서식** — `form: prose` 문서(소개 글, 발표 대본, 칼럼, 설명문)에서만 본다. 문단마다 「먼저 / 반면 / 결국」이나 「첫째 / 둘째 / 마지막으로」로 여는 공식, 문장 속 「1) 2) 3)」 번호, 「서론: ~」 같은 콜론 부제 제목과 도입·본론·결론 같은 도식 제목, 제목마다 붙인 「이 절에서는 ~를 다룹니다」 안내, 모든 문단의 첫 문장이 요약이고 문단 길이가 고르게 같은 것, 문장마다 굵게나 대시(—) 부연이나 「(이는 ~)」 괄호 부연을 얹은 것, 문단마다 「**굵은 라벨** — 설명」으로 여는 정의 공식, 발표 대본의 문장이 거의 다 「봅니다」·「살펴봅니다」·「설명합니다」로 끝나는 것, 에세이 결말의 「어쩌면 ~일 것이다」·「비로소」가 대상이다. **판정 — 그 서식을 걷어도 읽는 순서와 뜻이 같은지 본다.** 같으면 문장으로 녹인다. 개조식 문서(구조형)에서는 불릿, 「굵은 결론 — 근거」, 번호 목록이 이 저장소의 문서 규칙이라 이 항목으로 짚지 않는다.

   「일어난 일을 가능형으로 씀」부터 끝까지는 대외 기술 백서를 고치던 세션이 넘긴 것이다(2026-10-22). 판정기가 놓쳤거나 **반대 방향으로 고치라고 한** 사례라서 고칠 방향까지 적는다. 마지막 둘은 사용자가 아니라 그 세션의 AI 검토에서 나왔고, 판정 기록에서 판정기도 같은 수정안을 낸 것이 확인됐다.

   - **일어난 일을 가능형으로 씀** — 이미 난 사고나 확인된 결함을 「제때 멈추지 못할 수 있습니다」처럼 쓴 경우다. 원문이 결함 조건을 일반화한 may 를 사건 서술에 그대로 옮기면 생긴다. 사용자 말로 「보고서인데 할 수 있습니다??」. **판정 — 그 문장이 일어난 일을 서술하는지, 조건을 일반화하는지 가른다.** 일어난 일이면 과거형으로 쓰고, 가능형은 「그 업체는 보고서에서 ~할 수 있다는 점을 결함의 원인으로 밝혔습니다」처럼 출처가 밝힌 조건에만 남긴다. ⛔ **고칠 쪽은 가능형으로 쓴 줄이다** — 뒤에 맞게 단정한 줄을 앞 줄에 맞춰 「~할 수 있었습니다」로 흐리지 않는다. 판정기가 바로 그렇게 제안했다.
   - **조건에 따라 다른 효과를 항상 일어나는 일로 단정함** — 위 항목의 반대 방향이다. 「계측 코드를 넣어 측정하므로, 시험하는 코드는 크기가 크고 실행 시간이 깁니다」처럼 정도가 조건에 따라 다른 효과를 항상 일어나는 일로 썼다. 사용자 말로 「무조건 길어진다가 틀린 건 아닌데」. 이런 단정을 감싸려고 붙인 변명 문장(「~공통으로 따르는 특성입니다」)도 같이 나온다. **판정 — 그 효과가 늘 같은 크기로 일어나는지, 무엇에 따라 달라지는지 묻는다.** 달라지면 영향을 받는 범위와 달라지는 조건을 쓰고, 변명 문장은 지운다.
   - **긴 조건 서술을 「~하는 것입니다」로 닫음** — 「결함은 다음과 같습니다. 차량이 ~하는 중에 ~하면, ~하느라 제때 서지 못하는 것입니다」처럼 조건절 둘과 연결 어미 셋을 한 문장에 몰고 명사화로 닫은 경우다. 사용자 말로 「문장이 이상한데 왜 이럴까」. 「요점은 ~를 근거로 ~하는 것입니다」처럼 짧은 지정문은 정상이다 — 그 문서에서 판정기가 낸 수정안도 이런 짧은 지정문이라 같은 꼴이 아니다. **판정 — 「것입니다」 앞에 조건과 연결이 몇 겹인지 센다.** 둘 이상이면 조건과 결과를 짧은 문장으로 나누고, 일어난 일이면 과거형으로 쓴다.
   - **고지 문단의 소개 말투** — 고지, 면책, 저작권 문단에 「본 자료에는 ~를 담았습니다」처럼 소개 글 말투를 쓴 경우다. 「담다」는 소개 글과 보도자료에서는 정상이라 낱말로 못 가른다. **판정 — 그 문단이 무엇을 알리는 문단인지 본다.** 고지 문단이면 「본 자료는 ~를 설명하기 위한 자료입니다」처럼 자료의 성격을 밝히는 말로 쓴다.
   - **구체화하다 나열을 줄임** — 포괄 표현을 구체적인 수단 이름으로 바꾸면서 원래 범위에 든 수단 일부를 뺀 경우다. 판정기가 「여러 시험 데이터 지정 기능으로」를 수단 셋 중 둘만 남긴 「입력값 설정이나 스텁으로」로 바꾸자고 했다. **판정 — 고친 말이 원문이 덮던 대상을 모두 덮는지 본다.** 하나라도 빠지면 범위 축소다. 고친 말을 낼 때 나열을 줄이지 말고, 모두 적을 수 없으면 포괄 표현을 그대로 둔다.
   - **축이 다른 한정어 둘을 겹친 것으로 보고 하나를 지움** — 「지원되는 연동 구성에서는 가능한 범위에서 같은 시험을 장비에서 실행해」의 앞 한정어는 구성을, 뒤 한정어는 그 구성에서 돌릴 수 있는 시험을 좁힌다. 판정기가 뒤를 군더더기로 보고 세 번 지우자고 했고(「요약하다 맥락이 빠진 명사구」), 지우면 「지원 구성에서는 모든 시험이 장비에서 돈다」로 범위가 넓어진다. **판정 — 한정어마다 무엇을 좁히는지 먼저 적는다.** 대상이 다르면 둘 다 둔다. 「지워 보고 뜻이 통하면 군더더기」는 지운 뒤 범위나 확실성이 넓어지지 않을 때만 적용한다.
   - **같은 대상을 문서 안에서 두 이름으로 부름** — 같은 원어를 한 곳은 「AI 구성요소」, 다른 곳은 「AI 컴포넌트」로 쓰거나, 같은 시험 범위를 「통합 경계」와 「인터페이스 경계」로 섞은 경우다. 줄 하나만 보면 둘 다 멀쩡하다. 그 문서에서는 판정기 수정안이 「인터페이스 경계」를 새로 들여왔다. **판정 — 고친 말에 문서에 없던 용어가 들어가면 같은 대상을 부르는 기존 용어가 있는지 찾는다.** 있으면 문서 첫 정의나 작성자 원문의 표기를 쓴다. 기계 점검(같은 괄호 원어에 다른 한국어, 같은 머리 명사에 앞말만 다른 쌍)은 측정 전이라 안 넣었다.
10. 검사기가 지적한 것 중 오탐이 있는지 본다. 문맥상 정상이면 고치지 않고, `record_feedback.py`에 `--user-verdict false_positive`로 남긴다.
11. 오류가 없고 의미 보존 검사가 통과한 문서만 전달한다. 검사 실패와 검사할 수 없음을 합격으로 처리하지 않는다.
12. **문맥 판단을 마쳤다고 적는다** — 내용 해시에 묶이므로 **더 고치지 않을 내용**에서 적는다. 이 단계에서 적지 않으면 절차가 돌았다는 사실이 어디에도 안 남고, 발행 게이트가 2층을 요구할 근거도 안 생긴다.

```powershell
python -X utf8 ~/.claude/assets/check_record.py record <대상> --stage judgment --verdict <pass|fail> --note "<남긴 지적과 까닭>"
python -X utf8 ~/.claude/assets/check_record.py status <대상>
```

   - **push · 배포 게이트는 판정기를 부를 수 있으면 이 기록으로 막지 않는다** (2026-10-13) — 판정기 기록으로 새 줄 · 지운 자리를 직접 확인하고, 남긴 지적은 처리 기록 · 사용자 답을 요구한다. 그래도 적는다 — 2층이 실제로 도는 비율(`measure_layer2_uptake.py`)을 이 기록으로 잰다. 판정기를 못 부르는 PC 에서는 게이트가 이 기록을 요구한다.
   - **⛔ 시작을 완료로 세지 않는다** — 9단계를 끝까지 못 봤거나 사용자에게 물어보고 멈췄으면 적지 않는다. 고칠 것이 남은 채 끝났으면 `fail`.
   - **통과에는 까닭이 필수다** — 2층 판정기는 다시 불러도 늘 지적 몇 건을 내므로, 반영하지 않고 남긴 지적을 왜 두었는지가 곧 판정 내용이다(「남은 3건 — 굳은 용어 2 · 원문 인용 1」). 까닭이 없으면 기록기가 받지 않는다.
   - **내용이 바뀌면 다시 적는다** — 적은 뒤에 한 글자라도 고치면 그 기록은 지금 내용과 안 맞는다. `status` 로 확인한다.

## 수정 원칙

- 원래 의미·수치·고유명사·인용·계획 상태를 바꾸지 않는다.
- 자연스러움을 이유로 사실을 보충하거나 더 강하게 단정하지 않는다.
- 문서 종류의 말투와 구조를 유지한다. 보고서의 값 칸을 모두 완전한 문장으로 바꾸지 않는다.
- 사용자가 확정한 수정이 일반 규칙보다 우선한다. 다만 적용 문서 종류가 다르면 기계적으로 적용하지 않는다.
- 수정할 근거가 약하면 원문을 유지한다. 검사 결과 수나 변경률을 늘리는 것을 목표로 삼지 않는다.

## 사용자 교정 반영

사용자가 수정 전후 표현을 확정하면 먼저 후보 기록을 만든다. 후보 기록과 실제 검사 규칙은 분리한다. 모델이 찾은 표현은 `observed`, 사용자가 직접 고치거나 제안을 받아들인 표현은 `confirmed`로 저장한다.

```powershell
python scripts/record_feedback.py --candidate-id <고유-ID> --rule-id <규칙-ID> --original <수정-전> --revised <수정-후> --profile <문서-종류> --decision-source user_direct --user-verdict corrected --context-level <sentence|window|block|document>
```

미리보기를 확인한 뒤 같은 명령에 `--apply`를 붙이면 후보 목록에만 기록된다. 문맥은 수정 판단에 실제로 필요했던 만큼만 저장한다.

- `sentence`: 독립 문장이나 짧은 문구만으로 판정 가능
- `window`: 지시 대상·인과·진행 상태를 확인해야 함 · 앞문장이나 뒷문장 중 필요한 부분 저장
- `block`: 표·목록·슬라이드처럼 구조가 판단을 좌우함 · 절 제목이나 논리 위치 저장
- `document`: 문서 전체의 상태나 용어 정의를 확인해야 함 · 문서 사본 대신 원본 참조와 해시 저장

후보를 실제 규칙과 회귀 시료에 넣기 전에는 별도 미리보기를 만든다.

```powershell
python scripts/promote_feedback.py --candidate-id <고유-ID>
```

사용자 직접 수정·사용자 수락·사람 검토 중 하나가 근거이고, 판정이 `corrected` 또는 `accepted`인 후보만 승격할 수 있다. 같은 명령에 `--apply`를 붙이면 실행 중인 스킬과 `korean-writing-qa` 저장소의 규칙·시료 사본을 함께 갱신한 뒤 자체 시험을 실행한다. 두 사본이 작업 전에 다르면 중단한다. 시험이 실패하면 후보·규칙·시료·개수 명세를 원래 상태로 되돌린다. 모델이 찾은 후보와 거짓양성 기록은 자동으로 승격하지 않는다.

검사기 오류 수정, 형식 지원 추가, 실행 실패 처리처럼 언어 정책을 만들지 않는 기술 변경에는 사용자 확인을 요구하지 않는다. 대신 해당 실패를 재현하는 시험을 먼저 추가한다.

공통 문맥 규칙을 바꿀 때는 `references/context-cases.jsonl`의 수정 전후 시료도 함께 검토한다. 이 파일의 시료는 사람이 판정한 자연스러운 수정 기준문이다. 자체 시험은 기준문 14쌍의 구조와 의미 보존을 확인하지만 자연스러움 자체를 자동 합격 처리하지 않는다. `python scripts/self_test.py` 결과의 탐지·자연스러움 기준문·의미 보존 수를 따로 읽는다.

## 실패 처리

- 지원하지 않는 형식이거나 표시 문구를 하나도 읽지 못하면 중단하고 원본 종류를 보고한다.
- 검사기 실행 오류를 빈 결과로 바꾸지 않는다.
- 의미 보존 검사에서 값이 바뀌거나 새로 생긴 보호 표현이 있으면 수정문을 전달하지 않는다.
- 사라진 보호 표현을 인정하지 않은 채 전달하지 않는다. 확인한 것만 `--expect-removed`로 넘기고, 무엇을 지웠는지 사용자에게 알린다.
- 문맥상 적절한 수정이 불확실하면 해당 문장과 판단에 필요한 사실을 사용자에게 제시한다.
