# AI 투 교정의 품질과 반복 수정 효율 (2026-11-09~10)

**결론** — 검사기는 고친 양이 적고, 사람 판정에서 나빠진 표현이 두 차례 모두 0건. 나아진 비율은 다른 흐름보다 높지 않음. 규칙을 넣은 단순 요청은 더 많이 고치지만 뜻을 잃는 줄임과 굳은 용어 풀어 쓰기가 섞임. 반복 수정은 2층만 도는 검사기가 규칙 요청 반복보다 시간이 6편 모두 짧았으나, 1층까지 고치는 실사용 흐름은 앞서지 못함(아래 「실사용 흐름」). 모두 표본이 작아 탐색적(사전 기록 [plan.md](plan.md), 원자료 [result.json](result.json))

## 입력 오염과 다시 만든 문서(2026-11-10)

- **발견** — Gemini 문서 2편이 이 PC 의 전역 지시(문서 서술 규칙, 스킬 목록)를 받은 채 생성됨. agy(Gemini CLI)가 홈 폴더의 지시 파일과 스킬 목록을 호출마다 함께 보냄
- **확인 방법** — 「받은 지시 가운데 ○○ 규칙이 있으면 있음」을 묻는 시험 질문 셋(기사 매체 규칙, 개조식 규칙, 한글 문서 스킬). 처음에는 매체 이름까지 답함
- **다시 만든 방법** — 로그인 파일만 복사한 임시 홈 폴더에서 agy 를 실행. 시험 질문 셋이 모두 「없음」인 것을 확인한 뒤 같은 요청문으로 생성(`gen.json` 의 `clean_home`)
- **다른 두 모델** — Claude(`setting_sources=[]`)와 GPT(빈 `instructions`)는 같은 시험에서 지시를 받지 않음
- **다시 측정한 항목** — Gemini 2편의 일곱 흐름 전부, 측정 1b 판정, 측정 2. 오염된 문서와 결과는 작업 폴더의 `contaminated-gemini/` 에 보관

## 측정 1b — 바뀐 표현의 사람 판정(사용자 블라인드, 깨끗한 문서)

| 흐름 | 판정 표현 | 나아짐 | 비슷함 | 나빠짐 |
|---|---|---|---|---|
| 검사기 | 6 | 3 | 3 | 0 |
| 단순 요청 | 8 | 5 | 2 | 1 |
| im-not-ai | 10 | 7 | 1 | 2 |
| 규칙을 넣은 요청 | 8 | 4 | 2 | 2 |
| 규칙 요청 반복 | 8 | 3 | 3 | 2 |

- **방식** — 바뀐 표현을 기계 규칙으로 네 갈래(낱말 바꿈, 풀어 씀, 줄임, 문장 고쳐 씀)로 나누고 기호와 서식만 다른 것은 뺀 뒤, 흐름마다 갈래별 2건을 고정 씨앗으로 뽑음(30건: Gemini 16, GPT 13, Claude 1). 여러 흐름에서 같은 표현이 나왔으면 흐름마다 셈(합 40)
- **앞 회차 답을 이어 씀** — 오염 전 판정과 문서, 앞뒤 문맥, 바뀐 표현이 글자까지 같은 7건은 앞 답을 그대로 쓰고 23건만 새로 물음
- **나빠짐 — 굳은 기술 용어 풀어 쓰기** — 「반응형 UI와」 → 「화면이 기기 크기에 맞게 표시되며,」(규칙 요청과 im-not-ai)
- **나빠짐 — 보안 내용을 지운 줄임** — 「채널 생성과 2단계 인증 기반 보안 체계가 적용됩니다.」 → 「채널을 개설할 수 있습니다.」(규칙 요청 반복)
- **나빠짐 — 낱말 바꿈** — 규칙 요청 둘과 im-not-ai 의 「배포」 → 「배포하는」 변경, 단순 요청의 「현재」 → 「현재는」 변경
- **오염된 문서로 한 앞 회차** — 검사기 7건 모두 나아짐, 규칙 요청 둘 각 11건 중 나빠짐 1, im-not-ai 5건 중 나빠짐 2. 이번 회차와 같은 것은 검사기의 나빠짐 0뿐
- **방식 변경(사용자 지시)** — 사전 기록은 문서마다 여섯 판의 순위였음. 사용자 「거의 유사한 글을 나보고 다 읽어보라는건가」, 「일관된 규칙으로 분류해서 그것만 고르게」로 표현 판정으로 바꿈. 사전 기록의 문서 단위 가름(6편 중 5편)은 적용할 수 없어 쓰지 않음
- **한계** — 흐름마다 6~10건이라 차이를 판정할 수 없는 크기. 실사용 흐름(checker2)은 판정 표본에 넣지 않음

## 실사용 흐름(checker2, 2026-11-09 사용자 「지금 고칠 수 있는거 다 고쳐놓으세요」 뒤)

위 검사기 흐름은 1층 지적을 고치지 않고 사실 확인 수정안을 넣지 않아 실사용과 달랐음. 실사용대로 고친 흐름을 따로 돌림 — 사전 기록에 없던 흐름이라 탐색적

- **흐름** — 2층 판정과 수정안 반영(사실 확인 수정안도 작성자가 확인했다고 보고 반영) → 1층 오류 줄만 Opus 로 고침 → 고친 줄 재판정, 1층 오류가 없을 때까지 최대 3회. 문서 형식은 주간보고 구조형, 공지 공지형으로 지정

| 지표 | checker2 | 비교 |
|---|---|---|
| 152건 고침(운반 문서) | 122(대장 102, 예비 20) | 규칙을 넣은 요청 139, 위 검사기 93 |
| 심은 표현 없는 줄 변경 | 9/43 | 규칙을 넣은 요청 22/43 |
| AI 문서 1층 오류(형식 지정) | 6편 모두 0건 | 다른 흐름은 원문과 같은 수 |
| AI 문서 1층 오류(형식 미지정 기본 검사) | 48 → 17 | 규칙 요청 반복 47, 나머지 48 |
| 숫자나 이름이 바뀐 문서 | 2/6 | 단순 요청 2, 규칙 요청 2, 규칙 요청 반복 1, 검사기 0, im-not-ai 0 |

- **나쁜 소식 하나 — 효율** — 규칙 요청 반복보다 시간은 6편 중 4편, 비용은 3편에서만 적어 사전 기록 기준의 「효율 앞섬」이 아님. 1층 고침 호출과 사실 확인 수정안 반영 뒤 재판정이 더해짐(호출 30, 규칙 요청 반복 17)
- **나쁜 소식 둘 — 사실 확인 수정안을 그대로 넣은 결과** — Claude 주간보고의 「주말 기준 목표 진척률」이 「11월 13일(금) 기준」으로 바뀜. 같은 문서의 「다음 주 계획 (11월 9일 ~ 11월 13일)」에서 끌어낸 날짜라 맞지만, 원문에 없던 사실을 판정기가 넣은 것. 실제 사용에서는 작성자가 확인한 뒤 넣는 수정안이라 이 흐름이 실사용보다 위험한 쪽으로 기움
- **나쁜 소식 셋 — 지운 값** — Gemini 주간보고의 「(연동률 85.7%)」를 지움. 앞의 「14건 중 12건」으로 계산되는 값이지만 원문이 적은 값을 잃음
- **사람 확인으로 넘긴 지적** — Gemini 공지 2건(재판정 상한). 이 측정에서는 답하지 않고 끝냄
- **다른 흐름에 없는 기능** — 1층 오류(서술형 문단을 개조식으로 등)를 형식 지정 기준으로 모두 고침. 다른 흐름은 거의 못 고침
- **전후 비교 페이지** — 이 흐름의 여섯 편을 원문과 나란히 실은 페이지를 `showcase.py` 로 만듦(측정 결과 그대로, 사람 손 안 댐)
- **고친 측정 결함** — 1층 고침이 줄을 앞 판으로 되돌리면 그때의 지적이 다시 열려 판정기가 재판정을 미룸(종료 코드 6, Gemini 공지). 재판정 전에 열린 지적을 먼저 처리하게 고친 뒤 다시 돌림

## 자동 지표(측정 1b 보조)

- **1층 오류는 실사용 흐름만 줄임** — 목록 값의 서술형 종결 같은 구조 문제라 다른 흐름은 원문과 거의 같은 수. 검사기 흐름도 1층 지적을 고치지 않게 설계해(다른 흐름과 같은 조건) 실사용보다 불리함
- **원문에 없던 「A가 아니라 B」, 「결국」, 「~하는 이유입니다」** — 어느 흐름도 새로 만들지 않음
- **보호 표현 손실**(`check_meaning --strict`) — 위 표의 「숫자나 이름이 바뀐 문서」. 검사기(매번 전체 판정)는 3편

## 입력과 재현
